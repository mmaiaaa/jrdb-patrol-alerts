# JRDB pilot evidence and next experimental gates

Status: development record, 2026-09-12. Pilot sequence: `bytes-cafe-2019-02-07_0` (stationary indoor robot, as identified in the [original JRDB paper](https://arxiv.org/html/1910.11792v4)). No alert-pipeline performance has been measured. The numbers below are local user-reported outputs from the scripts committed through `369835b`; verify the actual input commit, archive hashes and output hashes in the experiment log before citing them in a submission.

## What has been checked

- The pilot has 1,726 common filename frame IDs in camera 0, upper/lower LiDAR and 3D labels. Filename agreement alone does not prove synchronized acquisition times or correct coordinate transforms.
- The 3D label file has 39,567 pedestrian-frame observations from 37 IDs; 14,518 are within an exploratory 3 m horizontal center radius and have `no_eval=false`. A run generator forms 37 contiguous near-field candidate runs from 17 IDs; median run length is 60 frames, maximum is the full 1,726 frames. At least one labeled person is within 3 m in **every pilot frame**, so the pilot has no all-around person-free frames under this provisional rule. It can probe start-of-recording occupancy and repeated alerts, but cannot by itself establish background false-alert rates or observed entries for the full-length runs. These are repeated observations and candidate intervals, not independently verified encounters.
- Nearly all 3D observations have `interpolated=true` (39,550/39,567), including every pilot observation within 3 m. The original JRDB paper describes a direct-annotation versus interpolated flag; the value distribution in this 2022 file is unusual relative to the original reported annotation cadence. Do not infer that all near-field positions were directly hand-labeled or silently discard all interpolated frames. Verify reference boundaries independently and report sensitivity.
- Camera-0 pose: 948 annotations on 834 frames; stitched pose: 16,414 annotations across 1,725 frames. All 948 camera-0 pose annotations match a same-frame, same-numeric-ID 3D pedestrian within 3 m; 11,576 near-field 3D frame/track pairs also match stitched pose IDs. These are diagnostic ID overlaps, not complete visibility labels. Pose absence is not proof of invisibility. The final image frame `001725` is absent from both checked pose image lists.
- The stitched pose image rows report width 752 while the corresponding stitched JPEG is 3760 pixels wide. Most visible/occluded pose keypoints have x beyond 752 but within the JPEG. In one uploaded, reduced-resolution visual inspection (frame `000879`), many dots follow people across the panorama. This is a qualitative one-frame registration check only; the dataset metadata remains discrepant and 3D-to-image calibration is unverified.

## Decisions to make before defining reference events

1. Separate **initial occupancy** (a person within the region at the first observed frame), **observed entry** (verified transition from outside to inside), **re-entry** (after a verified exit), and **unknown/censored** intervals. A person still inside at the last frame has a right-censored ending; the first-frame entrants have a left-censored beginning. Do not treat a brief threshold fluctuation as independent evidence of a new person or new security incident.
2. Draft the reference rule on development recordings: verified robot coordinate frame, center/surface distance convention, radius boundary, minimum eligible duration, handling of missing/`no_eval` frames, occlusion, interpolation and unavailable sensor evidence. The exploratory 3 m radius is not a selected operating point or a safety standard. Retain a sensitivity analysis at plausible radii selected before the untouched test.
3. Audit sampled candidate beginnings and endings and sampled negative intervals **without seeing the proposed model's alerts**. Save a review table with reviewer, timestamp/frame, classification, uncertainty reason and adjudication. Two independent reviewers, if available, improve credibility; if only one reviews, report that limit. 2D pose presence may support review but cannot define the negative class.
4. Locate true frame timestamps in the exact downloaded release or document the limits of an assumed nominal frame rate. No seconds-based detection delay or false alarms per hour until an exposure-time convention is fixed and audited.
5. Inventory every train recording, mark motion status from verified source metadata or inspection, then predeclare location/session groups. Keep all views and repeated recordings of the same location together. Restrict pilot to development; reserve separate validation and untouched final groups before performance tuning. If official test labels are used, distinguish a custom event protocol from official benchmark scoring.

## First implemented baseline and evidence gates

- Run actual inference on the native stitched 360-degree image (or its documented tiles) with all selected views counted in end-to-end runtime. The original JRDB study also segmented panorama images for its YOLO baseline; this is prior art, not our novelty. Compare ordinary alert rules on **the same cached predictions** before implementing encounter memory. Do not use annotation boxes or identities as online input. [Original JRDB study](https://arxiv.org/html/1910.11792v4)
- An image-only detector does not yield metric range by itself. A claimed 3 m alert must include a tested sensor-derived range method (for example, calibrated image/LiDAR association); use 3D labels only for reference/evaluation, never to fill missing predicted distances. If calibrated association fails, narrow the task and claims rather than using oracle range.
- Only after geometry, reference-review procedure, timing, prediction provenance and at least one moving sequence pass their gates should the protocol be frozen and held-out event accuracy, alert rate and delay evaluated. Retain null and adverse results, compare tuned conventional baselines fairly, and compute uncertainty across independent recording groups rather than treating frames as independent.

This note is descriptive and revisable. Changes to final task definitions after viewing held-out method performance are exploratory and must be recorded as such.

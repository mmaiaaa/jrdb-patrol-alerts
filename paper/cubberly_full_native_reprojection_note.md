# Cubberly: full development native 2D / 3D center projection check

**Status: exploratory annotation-consistency evidence, not an alert result.** All 1,296 frames of the moving Cubberly development recording were checked with `scripts/audit_jrdb_dev_native_2d_3d_reprojection.py`. The output matches 3D pedestrian IDs with the same-frame IDs in JRDB's five native `labels_2d_activity_social` files, restricts 3D centers to an exploratory 3 m XY radius and projects each annotated center under two coordinate-frame hypotheses. This is *not* the online detection or ranging path.

| Audit item | Label-upper hypothesis | Label-ego hypothesis |
| --- | ---: | ---: |
| Same-ID frame-camera pairs whose projected center is inside the 2D box, all 4,516 pairs | 3,470 (76.84%) | 3,826 (84.72%) |
| Inside box, 4,457 pairs with 2D `no_eval=false` | 3,470 (77.86%) | 3,826 (85.84%) |
| Outside box but inside image, 2D evaluable pairs | 396 | 57 |
| Outside image, 2D evaluable pairs | 591 | 574 |

The all-pairs and evaluable counts should **not** be analyzed as independent trials: the same person can appear in several cameras and many neighboring frames. These are center-inside-annotation-box checks, not a reprojection residual in pixels, measured sensor range, calibration accuracy, detector recall or evidence of time synchronization. JRDB's [original paper](https://arxiv.org/html/1910.11792v4) describes how 2D annotations were initialized with projected 3D boxes and refined, so the 2D and 3D annotations do not give independent geometric ground truth. The ego-frame interpretation is **provisionally more consistent** with these labels and the earlier four-frame visual inspection, but it has not been established as the true annotation convention. Preserve both hypotheses until separate geometry and raw-cloud checks resolve them.

The two printed ego-hypothesis exceptions deserve explicit review. At frame `000432`/camera 4, `pedestrian:33` has a 2D box `[0, 422.96, 28.22, 57.04]` on the left and bottom image edges, while its projected ego center is `(260.25, 215.88)`, 311 pixels from that box. At frame `000864`/camera 8, `pedestrian:22` has a box `[726.79, 136.24, 25.21, 243.07]` ending at the right image edge; its projected ego center is outside the image, even though its 2D `truncated` field says false. Image-edge clipping is a possible contributor, **not a verified explanation** for either disagreement. Inspect the full-resolution native images, actual person identity and annotation geometry on both frames; review unclipped ego failures as well to avoid selecting only favorable examples.

Run `scripts/summarize_jrdb_dev_projection.py` on the full CSV and source JSON to partition paired outcomes by camera, image-edge geometry, occlusion, truncation and person track. It also compares unique frame-track coverage and writes a prioritized review CSV. An edge-touching box is defined geometrically as extending to within 1 pixel of the 752 × 480 native image boundary; this intentionally does not rely on the annotation `truncated` flag. Report paired ego-only versus upper-only cases and track-level distributions alongside the raw totals. This is a quality-control table, not a significance test.

The next method milestone is a sensor-only per-detection range estimator tested against reference 3D positions **offline**, with foreground/background checks and explicit no-range outcomes. Then implement identity/duplicate handling and causal alerts from cached predictions, independently adjudicate reference encounter and negative intervals, verify original timestamps, select validation groups, and run a frozen evaluation on previously untouched moving recordings. No claim about end-to-end patrol reliability or security intrusion follows from the projection counts.

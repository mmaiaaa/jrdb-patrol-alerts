# Cubberly development: depth support and reference geometry (draft)

The five-camera YOLOv8n cache covers all 1,296 moving-development frames (6,480 camera images). This note reports **diagnostics**, not a proximity-alert evaluation. The cached prediction SHA-256 is `2e13fa212e647561765f0cc203ec60fd658e6377c6a7c655200700beddc56a16`; calibration SHA-256 is `ce76679a029bde9b934eaa8781273c3accbf7871ced47294940e79ed92a4ed01`.

An inner-box projection check on the four development frames `000087`, `000432`, `000864`, `001295` examined **142 raw detector boxes** (camera 0/2/4/6/8: 41/20/35/31/15). All 142 have at least one projected upper-LiDAR point in the central region. **130/142** have at least two distinct 0.5 m radial bins with three or more points each; **118/142** have supported radial bins at least 3 m apart. This last figure was computed from the same `inner_bins_counts_json` in the provided CSV. It is descriptive of returns **inside boxes**, not an error rate or a number of misranged people. The CSV's radius is measured from the upper LiDAR in the horizontal plane; multiple surfaces can appear in one box. In frame `001295`, camera 0's first raw box contains 399 central-region returns in the 2.0 m bin and 30 in the 10.0 m bin; neither group has been validated as the person's actual surface. Frame `000432`, camera 2's first raw box contains supported bins near 2–3 m and 6–6.5 m. Selecting the minimum or most populated bin would silently impose an untested foreground rule.

`scripts/audit_jrdb_dev_box_geometry.py` is a **separate offline reference check**. For the same four frames it loads annotated 3D pedestrian boxes and measured upper-cloud points. It reports how many upper returns lie inside each yaw-oriented 3D box under either of two explicit hypotheses: the annotation coordinates are upper-LiDAR coordinates, or they are ego coordinates after `lidar.upper2ego`. It also records `no_eval`, `interpolated`, box XY radius and annotated `num_points`. It uses box centers as geometric centers, length along local X, width along local Y and `rot_z` about Z. These conventions remain assumptions. The JRDB reported point count can include a different sensor set or filtering rule, so agreement in counts **cannot identify the correct coordinate convention on its own**. Read the resulting CSV alongside a few original images/point clouds and the annotation specification before using any 3D label as a distance reference. This script makes no 2D-to-3D identity match or person-range estimate and reads no detector prediction.

Next, inspect the output for disagreements, verify the 3D label frame convention against dataset documentation and an independently reviewed subset, check timestamps or measured camera/LiDAR offset, and specify a foreground/unknown-distance policy using only raw sensors. Independently annotate entry/exit boundaries and negatives before tuning on Cubberly; freeze the method and group-level split before opening held-out sequences. The stationary bytes-cafe pilot and moving Cubberly development set do not yet justify recall, false alarms per hour, alert latency, or deployable robot claims.
